# 미리보기 설문, 댓글 바로가기, 콘텐츠 중앙 정렬

2026년 11월 25일. 기준 소스는 `develop`의 `6b49099`이며 패키지 버전은 `7.3.52.2026`이다.

## 사용 방법과 확인 결과

| 기능 | 동작 | 확인 결과 |
|---|---|---|
| 미리보기 설문 | 항목이나 체크박스를 누르고 원래의 투표하기 버튼으로 제출한다. 참여 조건, 선택 한도, 결과 미리보기, 마감 상태는 디시 설문이 처리한다. | Chrome for Testing과 Firefox에 임시 설치해 실제 AI 활용 갤러리 게시글에서 원문 설문을 열었다. 두 엔진에서 원본 게시글 번호, 원문 선택 함수, 체크 상태와 선택된 항목의 일치를 확인했다. |
| 상세 화면 댓글 바로가기 | 현재 게시글의 전체 댓글 수를 표시한다. 초기 숫자가 임시 0이면 해당 게시글 양식의 서버 집계를 확인하고, 원문 AJAX가 갱신한 숫자가 있으면 이를 반영한다. 집계를 확인할 수 없으면 숫자를 비워도 버튼으로 이동할 수 있다. | 공개 상업영화 갤러리에서 원문과 버튼이 각각 4와 4로 일치했다. 별도의 댓글 없는 글에서는 0을 확인했다. 모의 화면에서 0 → 27 → 128 → 0, 천 단위 숫자, 다른 글과 미리보기의 댓글 제외를 검사했다. |
| 콘텐츠 중앙 정렬 | 팝업의 **화면 · 편의** 또는 옵션의 **화면/표시 빠른 설정**에서 켠다. 기본값은 꺼짐이다. 한 설정이 PC 일반·마이너·미니·인물 갤러리의 목록과 상세에 적용된다. | 설치형 테스트에서 두 설정 화면, 열린 페이지 반영, 백업 내보내기·복원과 네 종류 갤러리 경로를 검사했다. Chromium 프로필을 종료하고 다시 열어 설정 유지를 확인했다. Firefox에서도 두 화면의 토글과 열린 상세 페이지의 적용·해제를 확인했다. |

팝업과 옵션은 기존 토글과 설정 행을 사용한다. 플로팅 버튼의 스타일과 크기, 개추·비추 동작, 권한, 버전은 기존 값을 유지했다. 중앙 정렬을 끄면 해당 스타일시트가 제거된다.

## 설문과 댓글의 원문 동작

원문 `poll.js`는 체크 표시와 별도로 `.sel`이 붙은 항목의 `data-no`를 수집한다. 미리보기는 체크박스를 직접 조작해도 원문 `chk_vote`를 거치게 하고 표시 상태를 선택 결과에 맞춘다. 원문이 제출 요청을 시작하면 버튼을 잠그고, 거절이나 통신 실패 뒤에는 다시 사용할 수 있게 한다. 정상 응답 뒤에는 사이트가 결과 페이지로 이동한다. [원문 설문 스크립트](https://gall.dcinside.com/_js/poll.js)

기존 방식은 이미 로드된 문서에 HTML을 다시 썼다. 이때 같은 전역 변수를 재선언하는 스크립트가 초기화에 실패하는 경우를 모의 위젯에서 재현했다. 수정본은 검증된 동일 출처 게시글 주소를 설문 프레임의 현재 기록에 반영한 뒤 원래 설문 URL로 이동한다. 브라우저가 게시글 Referer와 새 스크립트 실행 환경을 제공한다. 상위 탭의 주소는 유지된다. 서버 권한 검사와 제출은 원문이 수행한다. [확인한 공개 설문 게시글](https://gall.dcinside.com/mgallery/board/view/?id=ai_utilize&no=65004)

별도 검사에서는 공개 `poll.js`와 jQuery를 메모리에 읽은 뒤 모든 브라우저 요청을 가로채는 모의 환경에서 실행했다. 실제 원문 코드가 선택한 두 항목을 `check_vote[]`로 보내는지, 두 번 클릭해도 한 건만 접수되는지, 모의 거절 후 재시도와 성공 응답 후 결과 페이지 이동이 되는지를 두 엔진에서 확인했다. 실사이트에 투표를 제출하거나 계정별 참여 권한을 변경하는 검사는 수행하지 않았다.

댓글 원문은 조회 응답의 `total_cnt`를 `#comment_total_게시글번호`에 기록한다. 실제 HTML에서 게시글 양식에는 양수인 댓글 수가 들어 있고 댓글 영역에는 아직 0이 남아 있는 경우를 확인했다. 바로가기는 렌더링된 댓글 행을 세지 않는다. [원문 댓글 스크립트](https://gall.dcinside.com/_js/comment.js)

## 레이아웃과 성능

1,600px 창의 실사이트에서 목록 열은 너비 840px를 유지하며 중심이 640px에서 800px로 이동했다. 상세 본문은 너비 900px를 유지하며 670px에서 800px로 이동했다. 좁은 창에서는 화면 왼쪽에서 콘텐츠를 읽을 수 있게 여백을 제한한다. **650px 창에서 PC 원문의 문서 너비는 ON/OFF 모두 1,515px였다.** 원문이 고정 폭으로 제공하는 이 화면에는 가로 스크롤이 남는다.

Windows의 Chrome for Testing 151.0.7922.34와 Playwright Firefox 153.0에서 같은 합성 댓글 1,000개를 둔 상세 화면의 숫자만 20회 변경했다. 기준본과 수정본을 각 엔진에서 한 번씩 실행했다.

| 지표 | Chromium 기준 → 수정 | Firefox 기준 → 수정 |
|---|---:|---:|
| 원문 숫자 변경부터 버튼 갱신까지 중앙값 | 110.2 → 10.0ms | 110 → 10ms |
| 갱신 지연 p95 | 115 → 10.3ms | 112 → 10ms |
| 갱신 중 문서·요소의 `querySelectorAll` 호출 | 40 → 0 | 40 → 0 |
| MutationObserver 콜백 | 20 → 20 | 20 → 20 |
| 메인 스레드 누적 작업 시간 | 199 → 135ms | 미측정 |

Chromium에서 해당 구간의 Long Task는 양쪽 모두 0회였다. JS 힙의 구간 변화량은 기준본 −421KB, 수정본 +88KB로 GC 시점의 영향을 받는다. 장시간 메모리 사용량과 브라우저 전체 CPU 사용률은 미측정이다.

별도 미리보기 검사에서는 2,000개 댓글을 준비한 뒤 페이지를 세 번 추가하고 30프레임 동안 스크롤했다. 고정 입력창이 없는 상태에서 스크롤 영역 좌표를 읽는 횟수는 두 엔진 모두 각 3회 측정에서 40 → 6회였다. 패널 크기가 바뀌면 위치를 다시 계산하고, 입력창이나 디시콘 선택기가 있으면 실제 위치로 겹침을 검사한다.

## 검사 및 설치

| package.json 검사 | 결과 |
|---|---|
| `test` | 기준본 60/60, 수정본 60/60 |
| `test:browser` | 선택 실행인 스크롤·상호작용 프로파일 네 개를 켠 전체 묶음 185/185. 마지막 좁은 창 보정과 모의 전송 필드는 관련 테스트 3/3으로 재확인 |
| `test:preview` | 미리보기 정화, 미디어, 설문, 키보드 포커스와 닫기 통과 |

| `test:extension` | Chromium 설치형 통합 검사 통과 |

검사는 각 스크립트의 Node 명령을 사용했다. 전체 브라우저 묶음은 동시 실행 파일을 2개로 제한했다. Playwright의 Windows DLL 사전 검사는 이 환경에서 실패해 실행이 확인된 브라우저 바이너리로 검사했다. 서명 배포본 업그레이드와 최소 지원 브라우저 버전 조합은 이번 검증 범위에 포함되지 않았다.

설치 폴더는 `dist/DCinside-Gallery-Blocker`, 공통 ZIP은 `dist/DCinside-Gallery-Blocker-7.3.52.2026.zip`이다. ZIP 안의 120개 항목과 루트 manifest를 확인하고 각 파일을 패키징 시점의 소스와 대조했다. Chrome은 압축을 푼 폴더를 확장 관리의 개발자 모드에서 로드한다. Firefox는 `about:debugging#/runtime/this-firefox`의 임시 부가 기능 로드에서 해당 폴더의 `manifest.json`을 선택한다.
